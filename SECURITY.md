# Security Policy

Vaerion is a local-first, AI-native development engine: append-only blake3-chained
journals, a fail-closed permission broker, one sanctioned network egress site (the
model gateway), and reproducible packaging. This page states how to report a
vulnerability and where the security substance of record lives. It summarizes the
documents of record — it does not replace them.

## Supported version

| Version | Status |
|---|---|
| `0.1.12-rc1` (current release line) | Supported — fixes land fix-forward on the main line |
| Earlier rc tags (`v0.1.7-rc1` … `v0.1.11-rc1`) | Not patched — released tags are immutable (never overwritten; see `docs/security/REMOTE-PROTECTION.md`); fixes ship in the next release candidate |

Within v0.1, surfaces evolve additively: nothing is removed or renamed
(`BETA-ONBOARDING.md`).

## Reporting a vulnerability

Do NOT open a public issue for a security finding.

The disclosure posture of record (`docs/security/RISK-LEDGER.md`, "Disclosure
posture") is: reports go directly and privately to the project owner, Auren,
at `auren@vaerion.dev` — the project identity this repository already uses
(`CONTRIBUTING.md`, commit identity).

Include:

- the command or API call, and the observed versus expected behavior;
- reproduction steps from a clean state;
- where possible, journal or receipt output demonstrating the finding.

Honest state: no automated private-vulnerability-reporting channel (security.txt /
private vulnerability reporting) is provisioned yet. That gap is tracked openly as
`RISK-LEDGER` R-7 (Founder-gated). This page does not claim a channel that does
not exist.

## Security documentation of record

- `docs/security/THREAT-MODEL.md` — the v0.1 threat model: trust boundaries
  (operator → loopback daemon → extension host / gateway egress), adversaries
  A1–A5, and the properties the architecture is required to hold
  (e.g. P-NO-EGRESS: exactly one transport egress site).
- `docs/security/MITIGATIONS.md` — the mitigation record: each threat mapped to
  its implemented control and its evidence class (T = automated test,
  C = constitutional check, L = layerlint boundary, I = code inspection).
- `docs/security/RISK-LEDGER.md` — the honest remaining-risk ledger (R-1..R-7)
  with severity, owner, and exit criteria, plus the disclosure posture.
- `docs/security/REMOTE-PROTECTION.md` — generated by `tools/remote-protect.ts`:
  the synchronization protection law applied and probed on the remote of record
  (no force-push, no deletion, linear history, admins included).

## Posture highlights

Stated only where the documents above support them:

- Local-first, no telemetry: the engine contains exactly one network egress site —
  the gateway transport (THREAT-MODEL P-NO-EGRESS; MITIGATIONS A4 rows). The
  constitutional check fails the run if any other module imports HTTP client
  primitives. `vae doctor` runs with no phone-home.
- The API daemon binds loopback only and refuses every non-loopback bind (E2001);
  every state-changing route requires the pairing token (E2000).
- Extensions are sha256-digest-pinned before execution (E2100) and run under
  explicit grants; the permission broker fail-closes ungranted calls.

## Release artifact trust chain (and its honest limit)

Release artifacts are reproducible (ADR-0016) and signed. `tools/dist-pack.ts`
emits `SHA256SUMS`, a `MANIFEST.json` (sha256 + blake3) with an Ed25519 signature
(`MANIFEST.json.sig`), and the public key beside the artifacts
(`dist/release-signing.pub`, manifest-bound). `dist/VERIFY.md` — generated at
pack time (the `dist/` directory is not tracked in the repository) — teaches
consumer verification with `tools/dist-verify.ts`, which resolves the key
explicit flag → key beside manifest → fail-closed.

Known limit, stated openly: release signing currently trusts the bootstrap
Ed25519 key tracked in the repository. The offline key ceremony that replaces it
is pending — `RISK-LEDGER` R-2, Founder gate F-3
(`docs/ga/FINAL-VERIFIED-REALITY-REPORT.md`). Until it closes, the signature
proves integrity against the published key; it is not yet an offline-identity
guarantee.
